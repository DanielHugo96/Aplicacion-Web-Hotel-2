# Reception — base de datos, procedimientos y seeds

BD `reception_db`. Autoridad de ocupación/admisión. Sin FK a personas/habitaciones de otras DB. [Comunes](../../03-contrato-comun.md).

## Tablas

| api_idempotency, outbox, inbox, audit_log | Comunes |

Cierre RECHAZADO se conserva junto con su respuesta 409; nuevo intento usa nueva clave. `calculo` es null en VALIDANDO/RECHAZADO y obligatorio desde CONFIRMANDO: `{alojamientoTotal,saldoAlojamiento,consumosPagadosAntes,consumosPendientes,consumosTotal,cobroAhora,totalGeneral,expectedPendingTotal}`. alojamientoTotal=precioInicial+penalidad; saldoAlojamiento=alojamientoTotal-adelanto; consumosTotal=consumosPagadosAntes+consumosPendientes; cobroAhora=saldoAlojamiento+consumosPendientes; totalGeneral=alojamientoTotal+consumosTotal; expectedPendingTotal=consumosPendientes. El evento final asigna consumosPagadosAlCerrar=consumosPendientes. El cálculo se congela antes de invocar Sales; no se recalcula en CONFIRMANDO. COMPLETADO exige receipt_sales y completed_at. Nunca borrar un cierre para recuperarlo.

Constraints: fechaSalida>=fechaEntrada; dinero>=0; adelanto<=precioInicial; costoPenalidad<=precioInicial, y con costoPenalidad>0 `motivo_penalidad` obligatorio; `medio_pago_adelanto`/`medio_pago` solo EFECTIVO/TARJETA/OTRO (null = NO_REGISTRADO en históricos); gate OCUPADA requiere idRecepcion; LIMPIEZA_PENDIENTE requiere ciclo; BLOQUEADA requiere block. Índice único parcial:

```sql
CREATE UNIQUE INDEX uq_recepcion_habitacion_activa
ON recepcion (id_habitacion)
WHERE estado_estadia IN ('ACTIVA', 'CERRANDO');

CREATE UNIQUE INDEX uq_cierre_vigente
ON cierre (id_recepcion)
WHERE estado <> 'RECHAZADO';
```

Índices recepcion(id_hotel,estado_estadia), (id_cliente,created_at), operacion_consumo(id_recepcion,estado), cierre(estado,next_attempt_at). FK circular gate → recepción no obliga recepción → gate; la función controla consistencia. `vencida` no se persiste: es derivado de fechas en la consulta.

## DDL de referencia

Fuente única; los scripts Flyway se derivan de aquí (V1 esquema, V2+ cambios). Tipos y CHECK explícitos:

```sql
CREATE TABLE recepcion (
  id                        int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  id_hotel                  int           NOT NULL,
  id_habitacion             int           NOT NULL,
  id_cliente                int           NOT NULL,
  cliente_snapshot          jsonb         NOT NULL,
  habitacion_snapshot       jsonb         NOT NULL,
  tarifa                    numeric(12,2) NOT NULL CHECK (tarifa > 0),
  fecha_entrada             date          NOT NULL,
  fecha_salida              date          NOT NULL,
  fecha_salida_confirmacion timestamptz,
  precio_inicial            numeric(12,2) NOT NULL CHECK (precio_inicial >= 0),
  adelanto                  numeric(12,2) NOT NULL CHECK (adelanto >= 0),
  medio_pago_adelanto       varchar(12)   CHECK (medio_pago_adelanto IN ('EFECTIVO','TARJETA','OTRO')),
  precio_restante           numeric(12,2) NOT NULL CHECK (precio_restante >= 0),
  total_pagado              numeric(12,2) NOT NULL CHECK (total_pagado >= 0),
  costo_penalidad           numeric(12,2) NOT NULL DEFAULT 0 CHECK (costo_penalidad >= 0),
  motivo_penalidad          varchar(300),
  estado_estadia            varchar(16)   NOT NULL CHECK (estado_estadia IN ('ACTIVA','CERRANDO','CERRADA')),
  observacion               varchar(500),
  archivada                 boolean       NOT NULL DEFAULT false,
  version                   bigint        NOT NULL DEFAULT 1,
  created_at                timestamptz   NOT NULL DEFAULT now(),
  CHECK (fecha_salida >= fecha_entrada),
  CHECK (adelanto <= precio_inicial),
  CHECK (costo_penalidad <= precio_inicial),
  CHECK (costo_penalidad = 0 OR motivo_penalidad IS NOT NULL)
);
CREATE UNIQUE INDEX uq_recepcion_habitacion_activa ON recepcion (id_habitacion)
  WHERE estado_estadia IN ('ACTIVA','CERRANDO');
CREATE INDEX ix_recepcion_hotel_estado ON recepcion (id_hotel, estado_estadia);
CREATE INDEX ix_recepcion_cliente ON recepcion (id_cliente, created_at);

CREATE TABLE room_gate (
  id_habitacion     int PRIMARY KEY,             -- id externo (hotel_db)
  id_hotel          int         NOT NULL,
  estado            varchar(24) NOT NULL CHECK (estado IN ('LIBRE','OCUPADA','LIMPIEZA_PENDIENTE','BLOQUEADA')),
  id_recepcion      int REFERENCES recepcion(id),
  cleaning_cycle_id uuid,
  block_id          uuid,
  room_version      bigint      NOT NULL DEFAULT 0,
  hotel_version     bigint      NOT NULL,
  updated_at        timestamptz NOT NULL DEFAULT now(),
  CHECK (estado <> 'OCUPADA' OR id_recepcion IS NOT NULL),
  CHECK (estado <> 'LIMPIEZA_PENDIENTE' OR cleaning_cycle_id IS NOT NULL),
  CHECK (estado <> 'BLOQUEADA' OR block_id IS NOT NULL)
);

CREATE TABLE operacion_consumo (
  operation_id uuid PRIMARY KEY,
  id_recepcion int         NOT NULL REFERENCES recepcion(id),
  id_venta     int         NOT NULL,
  tipo         varchar(12) NOT NULL CHECK (tipo IN ('VENTA','PAGO','ANULACION')),
  estado       varchar(12) NOT NULL CHECK (estado IN ('ABIERTA','FINALIZADA')),
  resultado    varchar(30),
  created_at   timestamptz NOT NULL DEFAULT now(),
  finished_at  timestamptz,
  UNIQUE (id_venta, operation_id),
  CHECK (estado <> 'FINALIZADA' OR resultado IS NOT NULL)
);
CREATE INDEX ix_operacion_recepcion_estado ON operacion_consumo (id_recepcion, estado);

CREATE TABLE cierre (
  closure_id        uuid          PRIMARY KEY,
  id_recepcion      int           NOT NULL REFERENCES recepcion(id),
  estado            varchar(20)   NOT NULL CHECK (estado IN ('VALIDANDO','CONFIRMANDO','COMPLETADO','RECHAZADO')),
  request_hash      char(64)      NOT NULL,
  request           jsonb         NOT NULL,
  cobro_declarado   numeric(12,2) NOT NULL CHECK (cobro_declarado >= 0),
  penalidad         numeric(12,2) NOT NULL CHECK (penalidad >= 0),
  medio_pago        varchar(12)   CHECK (medio_pago IN ('EFECTIVO','TARJETA','OTRO')),
  calculo           jsonb,
  receipt_sales     jsonb,
  cleaning_cycle_id uuid          NOT NULL,
  attempts          int           NOT NULL DEFAULT 0,
  next_attempt_at   timestamptz   NOT NULL DEFAULT now(),
  last_error_code   varchar(80),
  completed_at      timestamptz,
  CHECK (estado NOT IN ('CONFIRMANDO','COMPLETADO') OR calculo IS NOT NULL),
  CHECK (estado <> 'COMPLETADO' OR (receipt_sales IS NOT NULL AND completed_at IS NOT NULL))
);
CREATE UNIQUE INDEX uq_cierre_vigente ON cierre (id_recepcion) WHERE estado <> 'RECHAZADO';
CREATE INDEX ix_cierre_recuperacion ON cierre (estado, next_attempt_at);

CREATE TABLE bloqueo_habitacion (
  block_id      uuid         PRIMARY KEY,
  id_habitacion int          NOT NULL,
  id_hotel      int          NOT NULL,
  motivo        varchar(300) NOT NULL,
  request_hash  char(64)     NOT NULL,
  estado        varchar(12)  NOT NULL CHECK (estado IN ('ACTIVO','LIBERADO','RECHAZADO')),
  error_code    varchar(80),
  created_at    timestamptz  NOT NULL DEFAULT now(),
  released_at   timestamptz,
  CHECK (estado <> 'RECHAZADO' OR error_code IS NOT NULL)
);
CREATE INDEX ix_bloqueo_habitacion ON bloqueo_habitacion (id_habitacion, estado);
```

`api_idempotency`, `outbox`, `inbox` y `audit_log` usan el DDL común de [`03-contrato-comun.md`](../../03-contrato-comun.md).

## Esquemas JSONB

`cliente_snapshot` (inmutable tras el check-in):

```json
{"idCliente":100,"tipoDocumento":"DNI","documento":"90000100","nombre":"Cliente","apellido":"Uno","correo":"cliente.uno@hotel.test","estado":true,"version":1}
```

Obligatorios: `idCliente`, `tipoDocumento`, `documento`, `nombre`, `apellido`, `correo`, `version`. El service copia el valor del `ClienteVigente` de identity; nunca lo edita luego.

`habitacion_snapshot` (validado en el check-in):

```json
{"idHabitacion":101,"idHotel":1,"numero":"101","idCategoria":1,"categoriaNombre":"Individual","pisoNombre":"Primer piso","detalle":"Habitación individual con cama de 1.5 plazas, escritorio y baño privado.","precio":70.00,"hotelNombre":"Casa Sillar Lima Centro","estadoFisico":"LISTA","estado":true,"version":1}
```

`precio` es la tarifa congelada (se copia a `recepcion.tarifa`). No expone ocupación ni limpieza.

`request` del cierre (inmutable desde VALIDANDO):

```json
{"idRecepcion":1001,"idHabitacion":101,"costoPenalidad":0.00,"motivoPenalidad":null,"montoRecibido":57.00,"medioPago":"EFECTIVO","requestedAt":"2026-10-05T16:00:00Z"}
```

Obligatorios: `idRecepcion`, `idHabitacion`, `costoPenalidad`, `montoRecibido`, `medioPago`, `requestedAt`; `motivoPenalidad` obligatorio si `costoPenalidad > 0`.

`calculo` del cierre (obligatorio desde CONFIRMANDO):

```json
{"alojamientoTotal":70.00,"saldoAlojamiento":50.00,"consumosPagadosAntes":0.00,"consumosPendientes":7.00,"consumosTotal":7.00,"cobroAhora":57.00,"totalGeneral":77.00,"expectedPendingTotal":7.00}
```

Tipos: todos los importes `numeric(12,2)` redondeados HALF_UP; `expectedPendingTotal` congela lo que Sales debe pagar. El cálculo no se recalcula en CONFIRMANDO.

## Procedimientos / funciones

| Firma | Invariante |
|---|---|
| fn_checkin(p_request jsonb,p_cliente_snapshot jsonb,p_habitacion_snapshot jsonb) RETURNS int | Lock gate LIBRE; calcula tarifa/noches; inserta ACTIVA; gate OCUPADA; roomVersion++ |
| sp_recepcion_actualizar(p_id int,p_salida date,p_observacion varchar,p_version bigint) | Solo ACTIVA, misma identidad/habitación; recalcula precio, no adelanto/pagos; rechaza 409 si nuevo precioInicial<adelanto |
| sp_operacion_admitir(p_operation uuid,p_recepcion int,p_venta int,p_tipo varchar) | Lock recepción y luego operación; exige ACTIVA; valida tupla; rechazo tardío queda FINALIZADA/RECHAZADA; no revive una lápida |
| sp_operacion_finalizar(p_operation uuid,p_recepcion int,p_venta int,p_tipo varchar,p_resultado varchar) | Mismo orden de locks; inbox + upsert FINALIZADA con tupla completa; acepta llegada previa a admitir; resultado contradictorio se rechaza; no cambia dinero |
| sp_cierre_iniciar(p_closure uuid,p_recepcion int,p_request jsonb) | Lock ACTIVA y cero ABIERTAS; CERRANDO + cierre VALIDANDO; persiste solicitud/clave |
| sp_cierre_rechazar_monto(p_closure uuid) | CAS solo VALIDANDO → RECHAZADO; vuelve ACTIVA auditado; conserva cierre y respuesta 409 |
| sp_cierre_preparar_confirmacion(p_closure uuid,p_calculo jsonb) | CAS VALIDANDO → CONFIRMANDO; persiste cálculo validado e inmutable antes del HTTP |
| sp_cierre_completar(p_closure uuid,p_receipt jsonb) | Solo CONFIRMANDO; valida recibo contra cálculo congelado; una vez: COMPLETADO, CERRADA + gate LIMPIEZA_PENDIENTE, roomVersion++ y outbox |
| sp_habitacion_bloquear(p_block uuid,p_habitacion int,p_hotel int,p_motivo varchar) | Lock gate; persiste ACTIVO si LIBRE y bloquea; si no, RECHAZADO/409 durable. Mismo block+hash conserva decisión aun si gate cambia; payload distinto 409 |
| sp_habitacion_habilitar(p_habitacion int,p_ciclo uuid?,p_block uuid?) | Solo libera correlación actual; no toca estadías activas |
| sp_recepcion_archivar(p_id int,p_version bigint) | Solo CERRADA, archivada=true; no borrar importes/snapshots |
| sp_recepcion_anular_checkin(p_id int,p_motivo varchar,p_version bigint) | CAS ACTIVA → CERRADA con archivada=true; exige cero operaciones ABIERTAS y sin cierre vigente; libera gate a LIBRE con roomVersion++; outbox RecepcionActualizada + audit_log; sin limpieza, receipt ni cobro |
| sp_gate_inicializar(p_habitacion int,p_hotel int,p_fisico varchar,p_version bigint) | Bootstrap/alta de catálogo; solo crea gate ausente LIBRE si LISTA/activo; no sobreescribe un gate existente |

Bootstrap de habitación no admisible crea gate BLOQUEADA con block_id determinista de migración y bloqueo local auditado; nunca inventa LIBRE. En migración de ocupadas, se carga gate OCUPADA con su recepción antes de habilitar tráfico.

Las funciones trabajan con datos ya verificados por Feign. El service escribe eventos de salida en la misma transacción; jamás hace llamadas remotas desde el procedimiento.

## Seeds

No estadías ni cierres activos en seed base. Gate se crea al consumir las 6 HabitacionCreada del seed hotel; antes no se admite check-in. Para tests aislados sí cargar gates 101, 102, 201, 202, 301, 302 LIBRE usando fixture equivalente a evento, no en paralelo con broker.

Escenario por API, no SQL cruzado: cliente 100 y habitación 101, fechaEntrada=fecha actual en Lima, fechaSalida=mañana, tarifa 70, adelanto 20. Esperado precioInicial 70/saldo 50. La API genera idRecepcion; los tests guardan ese ID, no asumen 1001 del ejemplo.

No resetear gates/recepciones con seed reejecutable. Pruebas de limpieza/doble check-in usan transacciones/fixtures en DB efímera.

## Validación esencial

Dos check-ins 101 → 201 devuelven 409 en el segundo; room 101 de sede 1 y room 201 de sede 2 son independientes. Un cliente puede tener dos estadías ACTIVAS en habitaciones/sedes distintas (el índice parcial es por habitación, no por cliente); la auditoría de migración solo reporta duplicados como calidad de datos, sin bloquear. Rabbit detenido no libera gate después de cierre. Ciclo viejo ignorado. Mantenimiento concurrente/check-in: solo uno gana. CERRANDO bloquea ventas; finalización duplicada no cambia resultados. Finalizar antes de admitir crea fila completa con tipo; cierre CONFIRMANDO se recupera sin recalcular; bloqueo RECHAZADO no se admite al quedar libre después. Anular un check-in sin ventas admitidas ni cierre deja gate LIBRE y estadía CERRADA archivada, sin receipt ni limpieza; con operaciones ABIERTAS o cierre vigente devuelve 409 y no cambia nada.
