# Identity — base de datos, procedimientos y seeds

BD `identity_db`. Dueño exclusivo de personas, roles, sedes autorizadas y credenciales. No contiene estadías. Convenciones/tablas técnicas: [contrato común](../../03-contrato-comun.md).

## Tablas

Campos sin ? son NOT NULL. PK int GENERATED BY DEFAULT AS IDENTITY salvo catálogos/UUID.

| Tabla | Columnas y restricciones |
|---|---|
| tipo_persona | id:int PK; codigo:varchar(20) UNIQUE; descripcion:varchar(80); estado:boolean default true; version:bigint default 1. Solo ADMIN, EMPLEADO, CLIENTE |
| persona | id:int PK; tipo_documento:varchar(12) CHECK DNI/PASAPORTE/CE; documento:varchar(20); nombre:varchar(100); apellido:varchar(100); correo:varchar(254) UNIQUE normalizado; clave_hash:varchar(255)?; foto_url:varchar(500)?; id_tipo_persona:int FK local; estado:boolean default true; version:bigint default 1; created_at/updated_at:timestamptz; UNIQUE(tipo_documento,documento) |
| persona_sede | id_persona:int FK persona; id_hotel:int referencia externa; PK(id_persona,id_hotel). Solo personal |
| service_client | client_id:varchar(80) PK; secret_hash:varchar(255); audiencias_scopes:jsonb `{"<audiencia>":["scope",…]}`; estado:boolean. No comparte credencial humana |
| api_idempotency | Esquema común; registro público actor=hash del correo normalizado, no IP |
| outbox | Kafka personas y Rabbit bienvenida |
| audit_log | Altas/bajas, cambios de permisos y consultas humanas de PII ajena (`PERSONA_SEARCH`/`PERSONA_READ`); sin clave/hash; `changes` sin documento/correo en lecturas |

Persona sin clave_hash es huésped creado por recepción/personal, no tiene login; registro público no toma control de correo/documento existente, devuelve 409. No implementar recuperación de cuenta implícita. Vincular cuenta preexistente exige flujo verificado futuro.

DNI 8 dígitos; otros documentos 6–20 alfanuméricos; correo sintácticamente válido. Índices documento, correo y persona_sede(id_hotel,id_persona). Cambiar sede de empleado valida sede por Feign antes del commit. No FK a hotel_db.

## Procedimientos y funciones

| Firma propuesta | Regla/resultado |
|---|---|
| fn_persona_guardar(p_id int?, p_datos jsonb, p_sedes int[], p_expected_version bigint?) RETURNS persona | Alta/update de datos permitidos; clave_hash ya BCrypt desde Java; lock versión; no duplicados; reemplazo local de asignaciones; devuelve fila sin serializar hash al API |
| sp_persona_desactivar(p_id int,p_expected_version bigint,p_actor int) | Baja lógica; comparte el bloqueo y la protección del último ADMIN con fn_persona_guardar, incluso ante cambios por PUT |
| sp_persona_anonimizar(p_id int,p_actor int) | Solo persona inactiva > 5 años (procedimiento manual auditado): reemplaza nombre/apellido/documento/correo por valores de anonimización, conserva id, estado y version; registra `PERSONA_ANONYMIZE` en audit_log. No hay job automático |
| fn_cliente_vigente(p_id int) RETURNS TABLE(id int,nombre text,apellido text,tipo_documento text,documento text,correo text,version bigint) | Solo persona activa tipo CLIENTE, sin secreto |
| sp_tipo_persona_descripcion(p_id int,p_descripcion varchar,p_expected_version bigint) | Edita etiqueta, no código ni permisos; los 3 roles nunca se crean/eliminan por REST |

Toda alta/cambio de rol/estado/baja de persona bloquea primero la fila fija tipo_persona.codigo=ADMIN con SELECT FOR UPDATE y después la persona. Dentro de la misma transacción verifica que quede al menos un ADMIN activo con clave_hash. La fila de rol actúa como mutex aunque distintos admins se editen a la vez; no basta contar administradores antes de adquirir el lock. Invariante también en PUT con estado=false o degradación de rol. Convertir un huésped sin clave en ADMIN/EMPLEADO se rechaza 409 STAFF_CREDENTIAL_REQUIRED: no crear personal sin login ni inventar contraseña.

Login usa consulta por correo + BCryptPasswordEncoder.matches en Java; NO comparación de texto plano SQL. Cambiar contraseña se hace por service transaction con auditoría, no desde GET ni DTO de salida. Buscar/listar usa JPA con proyección sin hash.

Todas las mutaciones de persona producen PersonaSnapshot dentro de la misma transacción; registro público además genera bienvenida. No evento con documento, correo o clave para reporting.

## DDL de referencia

Fuente única; los scripts Flyway se derivan de aquí:

```sql
CREATE TABLE tipo_persona (
  id          int PRIMARY KEY,          -- 1 ADMIN, 2 EMPLEADO, 3 CLIENTE
  codigo      varchar(20) NOT NULL UNIQUE,
  descripcion varchar(80) NOT NULL,
  estado      boolean     NOT NULL DEFAULT true,
  version     bigint      NOT NULL DEFAULT 1
);

CREATE TABLE persona (
  id              int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  tipo_documento  varchar(12)  NOT NULL CHECK (tipo_documento IN ('DNI','PASAPORTE','CE')),
  documento       varchar(20)  NOT NULL,
  nombre          varchar(100) NOT NULL,
  apellido        varchar(100) NOT NULL,
  correo          varchar(254) NOT NULL UNIQUE,  -- normalizado a lowercase por el service
  clave_hash      varchar(255),
  foto_url        varchar(500),
  id_tipo_persona int          NOT NULL REFERENCES tipo_persona(id),
  estado          boolean      NOT NULL DEFAULT true,
  version         bigint       NOT NULL DEFAULT 1,
  created_at      timestamptz  NOT NULL DEFAULT now(),
  updated_at      timestamptz  NOT NULL DEFAULT now(),
  UNIQUE (tipo_documento, documento),
  CHECK (tipo_documento <> 'DNI' OR documento ~ '^[0-9]{8}$'),
  CHECK (tipo_documento = 'DNI' OR documento ~ '^[A-Za-z0-9]{6,20}$')
);
CREATE INDEX ix_persona_documento ON persona (tipo_documento, documento);

CREATE TABLE persona_sede (
  id_persona int NOT NULL REFERENCES persona(id),
  id_hotel   int NOT NULL,             -- id externo (hotel_db), validado por Feign
  PRIMARY KEY (id_persona, id_hotel)
);
CREATE INDEX ix_persona_sede_hotel ON persona_sede (id_hotel, id_persona);

CREATE TABLE service_client (
  client_id         varchar(80)  PRIMARY KEY,
  secret_hash       varchar(255) NOT NULL,
  audiencias_scopes jsonb        NOT NULL,   -- {"<audiencia>":["scope", ...]}
  estado            boolean      NOT NULL DEFAULT true
);
```

`api_idempotency`, `outbox`, `inbox` y `audit_log` usan el DDL común de [`03-contrato-comun.md`](../../03-contrato-comun.md); el esquema del `changes` de auditoría también está allí. Retención/anonymization: procedimiento manual auditado descrito en [privacidad](../../03-contrato-comun.md#privacidad-y-retención).

## Seeds

Perfil dev, idempotente, datos ficticios. Roles: 1 ADMIN/Administrador, 2 EMPLEADO/Empleado, 3 CLIENTE/Cliente.

| idPersona | correo | rol | sedes | documento DNI |
|---:|---|---|---|---|
| 1 | admin@hotel.test | ADMIN | global | 90000001 |
| 2 | recepcion.lima@hotel.test | EMPLEADO | 1 | 90000002 |
| 3 | recepcion.miraflores@hotel.test | EMPLEADO | 2 | 90000003 |
| 4 | recepcion.arequipa@hotel.test | EMPLEADO | 3 | 90000004 |
| 100 | cliente.uno@hotel.test | CLIENTE | ninguna | 90000100 |
| 101 | cliente.dos@hotel.test | CLIENTE | ninguna | 90000101 |

Nombres “Sillar Admin”, “Sillar Recepción Lima/Miraflores/Arequipa”, “Cliente Uno/Dos”. Activos, version 1. BCrypt calculado desde `DEMO_PASSWORD` del entorno; si no está definida, seed de usuarios no se ejecuta. Nunca usar claves reales ni repetir credenciales heredadas. Los correos `@hotel.test` son ficticios y de uso interno de la presentación: no se muestran en la landing ni se enlazan desde ella.

service_client: identity-service, reception-service, hotel-service, inventory-service, sales-service con credenciales diferentes desde entorno; scopes del contrato común y ampliaciones en APIs. No client secret de reporting/notification si no hacen Feign.

Secuencias se ajustan tras IDs explícitos. Reejecutar seed no restablece contraseña ni permisos modificados. Outbox de bootstrap publica snapshot por persona; audit/idempotency vacíos. No sembrar tokens/JWT.

## Validación

Correo/documento duplicado 409; E intentando crear ADMIN 403; hash no aparece en JSON/evento/log; dos bajas de último admin no dejan cero admins; cliente sin clave no entra; empleado de sede 1 no obtiene permisos de 2 enviando idHotel distinto.
